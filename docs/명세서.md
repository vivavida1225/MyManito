# MyManito 기획 명세서 (v1.4)

## 1. 앱 설명

**MyManito**는 카카오톡 로그인으로 사용자의 이름을 빠르게 파악할 수 있다는 점에 착안해, '마니또' 행사를 더 쉽고 간편하게 할 수 있게끔 지원하는 웹 애플리케이션이다.
Django DRF + Vue3의 조합으로 구현되며, Synology NAS의 Container Manager에서 단일/소수 컨테이너로 가볍게 구동될 수 있게끔 인프라 종속성을 최소화한다.
좁은 화면에서의 사용자 경험을 최우선으로 고려하는 **모바일 퍼스트(Mobile-First) 디자인**을 채택하여, 모바일 환경 접속 시 UI가 깨지지 않고 직관적으로 동작하도록 반응형 UI를 구현한다.

## 2. User Flow

1. 사용자는 앱 메인 페이지에 접속한 뒤 카카오톡으로 로그인하여, 시스템은 사용자의 실제 이름을 파악한다.
* **[추가]** 로그인 시 기본 프로필 정보 외에 **`talk_message` (카카오톡 메시지 전송)** 권한에 대한 동의를 필수로 받는다.


2. 로그인 후 사용자는 메인 대시보드에서 자신이 참여한 진행 중 팀과 종료 팀을 확인한다. 참여한 팀이 없으면 `새 팀 만들기`와 `기존 팀에 참여하기`를 주요 행동으로 제공한다.
3. 팀을 생성한 사용자가 해당 팀의 관리자다. 관리자는 본인이 참여한 경우에도 게임 진행 중에는 본인의 배정 결과 외에 타인의 매칭 결과를 알 수 없어야 한다.

### 2.1 관리자 역할 Flow

1. **팀 생성:** '새 팀 만들기' 버튼을 클릭하여 사용할 팀 코드를 입력한다. (공백 없는 임의의 문자열, 중복 불가)
2. **비밀번호 설정:** 관리자 페이지 접속용 비밀번호를 설정한다.
3. **참여자 등록:** 게임에 참여할 인원의 이름 정보를 입력한다. (콤마, 공백, 줄바꿈 등으로 구분)
4. **관리자 본인 참여 여부 확인:**
* '참여' 선택 시: 목록에 본인 이름이 없으면 추가 여부를 묻는 알림 제공.
* '미참여' 선택 시: 목록에 본인 이름이 있다면 제외 여부를 다시 확인.


5. **매칭 알고리즘 설정:** '자기 자신 지목'을 절대 배제하며, '상호 지목' 허용 비율을 설정한다. (기본값 20%)
6. **최종 확인 및 규칙 설정:** 파싱된 총원 N명을 최종 확인하고, 참여자들에게 보여줄 게임 규칙을 작성한다.
7. **초대:** 카카오톡 등을 통해 팀 코드와 접속 링크를 전파한다.
8. **대시보드 운영:** 관리자로 접속하여 진행 상황을 모니터링한다.
* **진행률 바:** "총원 10명 중 8명이 확인 완료" 직관적 표시.
* **미확인자 독려:** 아직 입장하지 않은(Unclaimed) 이름 목록을 확인하여 단톡방 등에서 수동으로 참여를 독려.
* **오매칭 초기화:** 유저가 다른 사람의 이름으로 잘못 입장한 경우, 해당 유저의 매칭 연결을 해제(초기화)할 수 있다.


9. **게임 종료 (안전장치 적용):** 행사가 끝나는 시점에 '게임 종료'를 진행한다. 실수 방지를 위해 모달창에 팀 코드(예: `서강대현우회여름`)를 직접 타이핑해야만 종료되도록 하드 캡챠(Hard Captcha)를 적용한다.

### 2.2 참여자 역할 Flow

1. **팀 입장:** '코드 입력해 팀에 참여하기'를 눌러 공유받은 코드를 입력하고, 규칙에 동의한다.
2. **이름 매칭 및 본인 확인 (Hijacking 방지):** 카카오톡 닉네임과 등록된 이름이 다를 경우, Unclaimed 목록에서 본인의 이름을 선택한다.
* 오선택 방지: 타인의 이름을 실수로 선택하는 것을 막기 위해, 선택 직후 팝업으로 재확인을 강하게 요구한다.


3. **결과 확인:** 시스템 알고리즘에 의해 지정된 상대방(내가 챙겨줄 사람)을 확인한다.
4. **1:1 익명 채팅 및 알림:** '나와 내 마니또', '나와 내가 챙겨줄 사람' 간의 1:1 채팅방에 입장한다. (익명 닉네임 설정 필요)
* **[추가] 카카오톡 '나와의 채팅방' 알림:** 상대방이 채팅을 보내면, 내 카카오톡의 '나와의 채팅방'으로 "익명 마니또로부터 새로운 메시지가 도착했습니다. [확인하러 가기]" 형태의 알림이 전송된다. 발신자가 철저히 블라인드 처리되어 익명성이 유지된다.
* **[추가] UX 안내 문구:** 앱 내에 "새 메시지 알림은 '나와의 채팅방'으로 조용히 배달됩니다. 푸시 알림(소리/진동)이 울리지 않으니 가끔 카카오톡을 확인해 주세요!"라는 가이드를 명시한다.


5. **결과 공개:** 관리자가 게임을 종료하면, 앱 접속 시 폭죽 애니메이션과 함께 나를 챙겨준 사람과 내가 챙겨준 사람이 공개된다. 모든 채팅 내역과 미디어는 이때 함께 파기된다.

## 3. 단순화된 기술 아키텍처 및 구현 방안

인프라의 복잡성(Redis, Celery 등)을 배제하고 Synology NAS 환경에서 단일 백엔드 컨테이너로 가볍게 돌아가도록 설계한다.

* **[추가] 카카오톡 API 연동 및 토큰 관리 (Token Refresh):**
* **토큰 저장:** 사용자가 카카오 로그인 시, DRF 백엔드는 유저 모델에 카카오 API 호출용 `Access Token`(수명 짧음)과 `Refresh Token`(수명 긺)을 함께 DB에 저장한다.
* **알림 발송 로직:** A가 B에게 메시지를 보낼 때, 백엔드는 **B의 토큰**을 사용하여 B의 '나와의 채팅방'으로 메시지 템플릿 API를 호출한다.
* **토큰 갱신(Refresh) 로직:** 알림 전송 전 B의 `Access Token` 만료 여부를 검증한다. 만료되었을 경우 DB에 저장된 `Refresh Token`을 이용해 카카오 Oauth 서버에 요청하여 새로운 `Access Token`을 발급받아 갱신한 후 알림을 발송한다.


* **실시간 채팅 (HTTP Polling):** WebSocket 인프라 대신, Vue3 프론트엔드에서 주기적으로(예: 3초 간격) DRF 엔드포인트를 호출하여 새 메시지를 가져오는 Short Polling 방식을 채택한다.
* **미디어 파일 자동 삭제 (APScheduler):** 수신자가 읽은 후 24시간이 지난 이미지를 지우기 위해 Django 내부 `APScheduler` 또는 서버 기본 Crontab을 활용해 1시간 주기로 DB를 스캔하고 파일/레코드를 삭제한다.
* **HTTPS 및 리버스 프록시:** 카카오 로그인 및 보안 통신을 위한 HTTPS는 Synology NAS의 내장 리버스 프록시 및 Let's Encrypt 자동 갱신 기능을 활용한다.
* **매칭 알고리즘:** 파이썬의 `random.shuffle()`을 활용하여 배정한 뒤 '자신 지목'과 '상호 지목 비율' 조건을 검사하고, 통과하지 못하면 다시 섞는 몬테카를로 방식(Rejection Sampling)을 사용한다.

## 4. 시스템 한계점 및 고려사항

1. **동명이인 처리:** 팀 내 '김민수'가 2명일 경우, 관리자가 '김민수A', '김민수B' 등으로 사전에 구별하여 입력해야 한다.
2. **[수정] 무음(Silent) 알림의 한계:** 카카오톡의 정책상 '나와의 채팅방'으로 전송되는 템플릿 메시지는 푸시 알림(상단바 팝업, 진동, 소리)을 발생시키지 않는다. 사용자는 카카오톡 앱을 열었을 때 보이는 '읽지 않은 메시지 뱃지(빨간 점)'를 통해서만 알림을 인지할 수 있으므로, 앱 내 가이드 문구를 통한 사용자의 사전 인지가 필수적이다.

## 5. 구현 보완 명세 (v1.4)

### 5.1 카카오 프로필 및 서비스 인증 세션

1. 카카오 로그인 시 `talk_message`, `profile_nickname`, `profile_image`, `account_email` 권한 동의를 모두 필수로 받는다. 닉네임, 프로필 이미지, 이메일을 모두 받지 못하면 서비스 로그인을 완료하지 않는다.
2. 카카오 `profile_nickname`을 서비스에서 사용하는 기본 이름으로 저장하며, 팀 참가자 이름 자동 선택 및 관리자 본인 참여 여부 확인에 사용한다.
3. 카카오 OAuth 인가 코드 요청에는 CSRF 방지용 `state` 값을 사용하고, 콜백에서 일치 여부를 검증한다.
4. 카카오 토큰과 별도로 서비스 전용 JWT access/refresh 토큰을 발급한다. 프론트엔드는 현재 세션 동안만 토큰과 카카오 프로필을 보관하고, 모든 API 요청에 access 토큰을 Bearer 방식으로 포함한다.
5. API 요청이 인증 만료(401)로 실패하면 refresh 토큰으로 access 토큰을 한 번 재발급한 뒤 원래 요청을 재시도한다. refresh도 실패하면 세션을 삭제하고 로그인 화면으로 이동한다.

### 5.2 팀 참가 확인 및 재입장 규칙

1. 한 사용자는 하나의 팀에서 하나의 참가자 이름만 Claim할 수 있고, 한 참가자 이름은 한 사용자만 Claim할 수 있다. 동시 요청에도 이 제약이 유지되어야 한다.
2. 관리자가 "나도 게임에 참여하기"를 선택하고 본인의 카카오 닉네임이 명단에 있으면, 생성 시 해당 참가자를 관리자 계정으로 자동 Claim한다.
3. 이미 Claim을 마친 참가자(관리자 포함)가 "코드 입력해 팀 참여하기"에서 같은 진행 중 팀 코드를 다시 입력하면, 새 이름을 선택하거나 재Claim하지 않는다. 규칙 동의 후 본인이 챙겨줄 사람만 다시 조회하여 결과 화면을 표시한다.
4. 팀 상세 조회, 미확인 이름 목록, 내 배정 결과 조회는 각각 필요한 최소 정보만 반환한다. 참여자 전체의 매칭 관계나 타인의 배정 결과는 어떤 경우에도 노출하지 않는다.
5. 관리자 대시보드와 관리자 작업은 팀 생성자 카카오 계정(팀 소유자)만 수행할 수 있다. 별도의 팀별 관리자 비밀번호나 인증 토큰은 사용하지 않는다.

### 5.3 채팅방 식별, 읽음 및 익명 닉네임 UX

1. Claim을 마친 참여자는 자신과 인접한 마니또 관계별로 최대 두 개의 채팅방을 가진다: "내가 챙겨줄 사람" 방과 "나를 챙겨주는 마니또" 방이다.
2. 채팅방 목록에는 관계 이름, 상대방의 Claim 완료 여부, 읽지 않은 메시지 수와 함께 **팀 코드**를 표시한다. 팀 코드는 카드 오른쪽 상단에 보조 정보로 표시한다.
3. 채팅방 내부 헤더에도 팀 코드를 표시하여 여러 팀에 동시에 참여했을 때 현재 대화의 소속 팀을 식별할 수 있어야 한다.
4. 채팅방 내부 우측 상단의 설정(톱니바퀴) 버튼으로 해당 팀에서 사용할 **내 익명 닉네임**을 설정하거나 변경할 수 있다. 닉네임은 최대 50자이며, 상대방에게만 표시된다.
5. 텍스트와 이미지 첨부를 전송할 수 있다. 이미지 선택은 모바일 화면에 맞는 이미지 아이콘 버튼으로 제공하며, 파일 선택 후에는 선택한 파일명을 표시한다.
6. 채팅방을 열어 메시지를 조회하면 상대방이 보낸 읽지 않은 메시지를 읽음 처리한다. 이 읽음 시각은 읽은 지 24시간이 지난 이미지 첨부파일 정리 기준으로 사용한다.

### 5.4 게임 종료 예정일 및 카운트다운 API

1. 관리자는 팀 생성 시 게임 **종료 예정일**만 선택할 수 있다. 시간·분 입력은 제공하지 않으며, 브라우저가 감지한 관리자 현재 지역의 IANA 시간대와 함께 저장해 관리자 지역 날짜 기준으로 일정을 해석한다.
2. 종료 예정일은 안내용 정보일 뿐 Team의 실제 상태를 변경하지 않는다. 예정일이 지나도 게임은 `ACTIVE` 상태를 유지하며, 관리자 대시보드의 하드 캡챠를 통과한 "게임 종료" 버튼으로만 `ENDED` 처리할 수 있다.
3. 본인 확인을 완료한 참가자는 `GET /api/teams/{code}/countdown/`으로 종료 예정 정보를 조회할 수 있다. 응답에는 `planned_end_date`, `planned_end_timezone`, `remaining`, `remaining_days`를 포함한다. 종료 예정일을 설정하지 않은 팀은 `remaining`과 `remaining_days`를 `null`로 반환한다.
4. `remaining`은 종료 예정일 전에는 `D-N` 형식으로 반환한다. 저장된 관리자 지역 시간대에서 종료 예정일의 자정(00:00)이 된 이후에는 실제 종료 여부와 관계없이 항상 정확히 `D-Day!`를 반환한다.
5. 팀 관리자는 진행 중(`ACTIVE`)인 팀의 관리자 대시보드에서 종료 예정일을 수정할 수 있다. 수정 API는 `PATCH /api/teams/{code}/admin/planned-end/`이며, 팀 소유자만 호출할 수 있다.

### 5.5 종료 팀 보존 및 자동 정리 정책

1. 게임 종료 즉시 해당 팀의 채팅 메시지와 첨부파일은 영구 파기한다. 결과 공개를 위해 팀, 참가자, 배정 정보는 종료 시각부터 7일 동안 유지한다.
2. Django 내부 APScheduler는 매시 정각에 종료 시각이 7일 이상 지난 팀을 정리한다. 정리 시 남아 있는 채팅·첨부파일을 다시 안전하게 제거한 뒤 Team과 Participant 레코드를 영구 삭제한다.
3. 팀 레코드가 삭제되면 종료 팀의 결과 공개는 더 이상 불가능하다. 대신 기존 팀 코드의 유니크 제약이 해제되어 같은 코드를 새 팀 생성에 다시 사용할 수 있다.
4. APScheduler는 단일 백엔드 프로세스에서만 실행한다. NAS 배포 시 스케줄러가 중복 실행되지 않도록 백엔드 컨테이너를 단일 인스턴스로 유지한다.

### 5.6 게임 종료 후 결과 공개 방식

1. 관리자는 팀 생성 시 결과 공개 방식을 하나 선택한다. 기본값은 **참가자 자동 공개**다.
   - 참가자 자동 공개: 게임 종료 후 모든 참가자가 앱에서 자신을 챙겨준 사람과 자신이 챙겨준 사람을 동시에 확인한다.
   - 관리자 외부 공개: 게임 종료 후 관리자만 전체 마니또 배정표를 확인하고, 행사·발표 등 플랫폼 외부 방식으로 결과를 공개한다.
2. 공개 방식 선택란 바로 옆에는 두 방식의 결과와 익명성 영향을 설명하는 도움말을 표시한다. 공개 방식은 팀 생성 시 확정되며 진행 중에는 변경할 수 없다.
3. 관리자 외부 공개 방식에서는 게임 종료 직후 참가자의 결과 조회 API가 결과를 반환하지 않고 "마니또 결과는 관리자가 별도로 공개합니다." 안내를 반환한다. 외부 행사 후 관리자가 공개 완료 처리를 하면 참가자는 자신의 결과를 조회할 수 있다.
4. 관리자 외부 공개 방식의 전체 배정표와 공개 완료 처리는 게임 종료 후 팀 소유자만 접근할 수 있는 관리자 대시보드에서만 제공한다. 게임 진행 중에는 관리자도 전체 배정표를 조회할 수 없다.

## 6. 프론트엔드 UX·정보 구조 명세 (v1.4)

이 절은 [UX 플로차트](assets/flowchart.png)를 기준으로, 다음 작업자가 화면 설계와 프론트엔드 구현에 바로 사용할 수 있는 기준이다. 화면은 모바일 퍼스트로 구성하되 데스크톱에서는 모바일 폭의 중앙 컨테이너를 유지한다.

### 6.1 전역 진입과 상단 네비게이션

1. 앱 최초 진입 시 카카오 로그인 상태를 확인한다.
   - 로그인 상태가 없으면 카카오 로그인 화면을 표시한다.
   - 로그인 상태가 있으면 메인 대시보드로 이동한다.
2. 로그인 후 모든 주요 화면에는 상단 네비게이션을 제공한다.
   - 로고: 메인 대시보드로 이동한다.
   - 알림: 읽지 않은 채팅, D-Day, 상대방 본인 확인 완료, 결과 공개 가능 등 팀별 이벤트를 모아 보여준다.
   - 채팅: 사용자가 Claim한 모든 팀의 채팅방 목록으로 이동한다.
   - 관리자 팀 현황: 현재 사용자가 소유한 팀이 하나 이상일 때만 노출한다. 팀이 여러 개면 먼저 팀을 선택한다.
3. 알림은 앱 내 알림함이며, 카카오 '나에게 보내기' 알림을 대체하지 않는다. 새 메시지의 카카오 알림 정책은 기존 명세를 따른다.

### 6.2 메인 대시보드와 팀 목록

1. 메인 대시보드는 다음 영역을 순서대로 제공한다.
   - `새 팀 만들기`, `기존 팀에 참여하기` 주요 행동
   - 진행 중인 팀 목록
   - 종료 팀 목록(보존 기간 내)
2. 팀 카드는 최소한 팀 코드, 관리자 여부, Claim 상태, 종료 예정일의 D-Day 정보, 읽지 않은 메시지 수, 결과 공개 상태를 표시한다.
3. 진행 중 팀 카드를 선택하면 팀 홈으로 이동한다. 팀 홈에서는 다음 행동을 제공한다.
   - 종료일까지 남은 날짜 조회
   - 내가 챙겨줄 사람 다시 보기(Claim 완료자만)
   - 해당 팀의 채팅방 목록으로 이동
   - Claim 미완료 상태라면 팀 코드 입장·이름 확인 흐름으로 유도
4. 종료 팀 카드는 공개 상태에 따라 다르게 표시한다.
   - 자동 공개 또는 관리자 공개 완료: `결과 확인` 행동을 노출하며, 선택 시 폭죽 효과와 함께 내 결과를 표시한다.
   - 관리자 외부 공개 대기: `관리자의 확인을 기다려 주세요` 상태를 표시하고 결과 정보는 노출하지 않는다.
5. 종료 팀과 참가자 정보는 종료 후 7일까지만 표시한다. 자동 정리 후에는 목록과 결과 화면에서 제거된다.

### 6.3 팀 생성·참여 UX

1. 신규 카카오 사용자와 기존 사용자 모두 메인 대시보드에서 새 팀 생성 또는 기존 팀 참여를 선택할 수 있다.
2. 새 팀 생성 폼은 기존 생성 항목에 더해 다음을 명확히 제공한다.
   - 관리자 본인 참여 여부
   - 종료 예정일(날짜만 입력, 관리자 지역 시간대 기준 자정부터 D-Day)
   - 종료 후 결과 공개 방식: `참가자 자동 공개`와 `관리자 외부 공개` 중 하나를 라디오 선택
   - 각 공개 방식의 결과와 익명성 영향에 대한 도움말
3. 기존 팀 참여는 `팀 코드 입력 → 규칙 확인·동의 → 이름 확인 또는 기존 Claim 복구 → 내가 챙겨줄 사람 확인` 순서다.
4. 카카오 닉네임이 미확인 참가자 이름과 정확히 일치하면 해당 이름을 자동 선택한다. 그래도 Claim 전에 강한 확인 모달을 반드시 표시한다.
5. 카카오 닉네임이 다르면 미확인 이름 목록에서 직접 선택하게 한다. 이미 Claim된 이름은 목록에 표시하지 않는다.

### 6.4 채팅 UX

1. 채팅 목록은 팀을 가로질러 보여 주되, 각 방에 관계(`내가 챙겨줄 사람`/`나를 챙겨주는 마니또`), 팀 코드, 상대방 Claim 상태, 읽지 않은 수를 표시한다.
2. 채팅방 선택 후에는 다음을 제공한다.
   - 팀 코드가 보이는 헤더와 뒤로가기
   - 수신/발신 메시지 말풍선, 이미지 첨부, Short Polling 기반 새 메시지 수신
   - 상대방이 아직 Claim하지 않았으면 전송 영역 대신 대기 상태 안내
   - 이미지 첨부 아이콘 버튼과 선택 파일명 표시
3. 채팅방 설정에서 사용자는 **채팅방별** 익명 닉네임과 프로필 이미지를 설정할 수 있다.
   - 기본 프로필 이미지를 제공하며, 사용자는 채팅방 단위로 다른 이미지를 지정할 수 있다.
   - 이 닉네임과 이미지는 해당 상대방에게만 표시하며, 카카오 실명·프로필을 대신 노출하지 않는다.
4. 메시지를 열람하면 상대방이 보낸 메시지를 읽음 처리한다. 읽음 수와 읽음 시각은 상대방에게 공개하지 않는다.

### 6.5 관리자 대시보드 UX

1. 관리자 대시보드는 팀 소유자(팀을 만든 카카오 계정)만 접근한다.
2. 진행 중 팀에서 제공할 관리 기능은 다음과 같다.
   - 총원/Claim 완료 수 진행률, 미확인자, 확인 완료자 조회
   - 오매칭 Claim 연결 해제
   - 종료 예정일 설정·수정
   - 게임 종료와 결과 공개 방식 확인
   - 잘못 만든 팀을 위한 팀 삭제
3. 팀 삭제는 되돌릴 수 없는 작업이다. 팀 코드 재입력 확인 모달을 거쳐야 하며, **관리자 본인 외에 Claim한 참가자가 없는 진행 중 팀**에서만 허용한다. 그 외에는 게임 종료와 7일 보존 정책을 따른다.
4. 게임 종료 전에는 공개 방식과 무관하게 전체 마니또 배정표를 표시하지 않는다.

### 6.6 게임 종료와 결과 공개 상태

1. 게임 종료 버튼은 기존 하드 캡챠를 통과해야 한다. 종료 즉시 채팅 메시지와 첨부파일을 파기한다.
2. `참가자 자동 공개` 방식:
   - 종료와 동시에 결과 공개 상태가 된다.
   - 종료 팀 카드의 `결과 확인`을 누르면 폭죽 효과와 함께 개인 결과를 표시한다.
3. `관리자 외부 공개` 방식:
   - 종료 직후 상태는 `관리자 외부 공개 대기`다.
   - 관리자만 전체 배정표를 확인해 플랫폼 외부 행사·발표를 진행한다.
   - 행사가 끝난 뒤 관리자는 대시보드의 `외부 공개 완료 및 참가자 결과 열기` 버튼을 눌러 결과 공개 상태로 전환한다. 이 버튼도 되돌릴 수 없음을 알리는 확인 모달을 제공한다.
   - 전환 전 참가자는 결과 카드에서 `관리자의 확인을 기다려 주세요`를 본다. 전환 후에는 자동 공개 방식과 동일하게 자신의 결과를 확인할 수 있다.

### 6.7 화면 상태와 공통 UX 규칙

1. 각 데이터 조회 화면은 로딩, 빈 상태, 권한 없음, 네트워크 오류, 재시도 상태를 제공한다.
2. 파괴적 행동(Claim 확정, 연결 해제, 팀 삭제, 게임 종료, 외부 공개 완료)은 목적과 되돌릴 수 없음을 명시한 확인 모달을 사용한다.
3. 이름·배정·카카오 토큰 등 민감 정보는 UI와 API 모두에서 권한이 있는 최소 범위에만 노출한다.
4. 버튼은 터치하기 쉬운 크기를 유지하고, 색상만으로 상태를 구분하지 않으며, 아이콘 버튼에는 접근성 레이블을 제공한다.

## 7. UX 구현을 위한 API·데이터 선행 조건

다음 계약은 6장의 화면을 완성하기 위해 백엔드와 합의해야 하는 항목이다. 아직 제공되지 않은 항목은 프론트엔드에서 임의 데이터로 대체하지 않는다.

1. `GET /api/teams/mine/`: 로그인 사용자의 진행 중/종료 팀 목록과 카드 표시용 정보(팀 코드, 소유자 여부, Claim 상태, 공개 상태, D-Day, 읽지 않은 수)를 반환한다.
2. `GET /api/notifications/`, `POST /api/notifications/{id}/read/`: 팀별 알림 목록과 읽음 처리를 제공한다. 메시지·D-Day·상대 Claim·결과 공개 이벤트를 구분할 수 있어야 한다.
3. `DELETE /api/teams/{code}/`: 팀 소유자만 호출할 수 있으며, 6.5의 안전 조건을 서버에서도 강제한다.
4. 관리자 외부 공개 방식에는 `reveal_status`가 필요하다. 최소 상태는 `AUTO_RELEASED`, `MANUAL_PENDING`, `MANUAL_RELEASED`이며, `POST /api/teams/{code}/admin/release-results/`는 `MANUAL_PENDING`에서만 `MANUAL_RELEASED`로 전환한다.
5. 채팅방별 프로필 설정 API는 닉네임과 이미지 업로드/기본 이미지 선택을 지원해야 한다. 프로필 데이터는 사용자·팀·상대방 관계에 종속되며, 다른 채팅방에 자동 공유되지 않는다.
6. 기존 `GET /api/teams/{code}/countdown/`은 팀 홈과 팀 카드의 D-Day 표시를 위한 기준 API로 사용한다. 종료 예정일이 없으면 D-Day UI를 숨기거나 `미설정`으로 표시한다.
